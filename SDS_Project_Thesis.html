1. Introduction

Seven Delivery Service (SDS) is a real-time courier and parcel delivery management system built using Flutter. It provides a single application that serves two types of users — Administrators and Delivery Riders — with role-based dashboards and functionality.

The application connects to a cloud-hosted PostgreSQL database via Supabase and provides real-time updates using streaming WebSocket subscriptions. Changes made by any user are reflected instantly across all connected devices without manual refreshing.

The system handles the full lifecycle of a delivery:

Order Created → Rider Assigned → QR Verified → Delivered

2. Problem Statement

Delivery companies in the UAE need a lightweight, unified system to:

  • Track orders in real-time across their full lifecycle
  • Manage a fleet of delivery riders with status tracking
  • Assign orders to riders — automatically (load-balanced) or manually
  • Verify parcel handover via QR code scanning
  • Generate analytics and performance reports
  • Allow riders to view their own deliveries and toggle availability
  • Work across multiple platforms (mobile, web, desktop) from a single codebase

SDS solves all of these requirements in a single cross-platform application.

3. System Architecture

The application follows a Service-Model-View architecture pattern:

  • Views (Screens) — Flutter widgets the user interacts with
  • Services — Dart classes that handle business logic and communicate with Supabase
  • Models — Dart classes that represent database table rows as typed objects

6. Supabase Integration

6.1 Connection Setup

The Supabase connection is established at app startup in main.dart before any widget renders:

void main() async {
  WidgetsFlutterBinding.ensureInitialized();

  await Supabase.initialize(
    url: 'https://lpenvkxvtpdbrzrmhrhg.supabase.co',
    anonKey: 'sb_publishable_y0cDWZ6idLhcl78_...',
  );

  runApp(const SevenDeliveryApp());
}

The centralized connection is managed by SupabaseService, which every service class accesses:

class SupabaseService {
  static const String supabaseUrl = 'https://lpenvkxvtpdbrzrmhrhg.supabase.co';
  static const String supabaseAnonKey = 'sb_publishable_...';

  static SupabaseClient get client => Supabase.instance.client;
}

6.2 Real-Time Streaming

Instead of polling or manual refreshing, SDS uses Supabase's Realtime feature. When any row in a table changes (insert, update, or delete), the app receives the update instantly via a WebSocket connection:

// This returns a Stream that emits new data whenever the orders table changes
_client.from('orders')
    .stream(primaryKey: ['id'])
    .order('id', ascending: false)
    .map((data) => data.map((json) => OrderModel.fromJson(json)).toList());

Real-time streaming is used for:

  • Orders list — new orders appear instantly on all screens
  • Riders list — status changes (available ↔ unavailable) reflect immediately
  • Activity logs — new log entries stream to the admin dashboard live

7. Authentication System

7.1 Login Flow

The app uses Supabase Auth (GoTrue) — a full authentication system with email + password login.

Future<AuthResponse> signIn(String email, String password) async {
  return await _client.auth.signInWithPassword(
    email: email,
    password: password,
  );
}

This sends the credentials to Supabase, which validates them and returns a JWT token (JSON Web Token). The token is stored in memory and sent with every subsequent database request to prove the user's identity.

7.2 Session Management

An AuthGuard widget in main.dart listens to auth state changes using a StreamBuilder:

StreamBuilder<AuthState>(
  stream: Supabase.instance.client.auth.onAuthStateChange,
  builder: (context, snapshot) {
    final session = Supabase.instance.client.auth.currentSession;

    if (session == null) return const LoginScreen();      // → Login
    return const MainNavigationScreen();                   // → App
  },
);

If the user logs out or the session expires, the app automatically returns to the login screen.

7.3 Rider Account Creation (Dual Strategy)

When an admin registers a new rider, the system creates both:

  1. A database row in the riders table (profile data)
  2. A Supabase Auth account so the rider can log in with email + password

This uses a platform-aware approach:

PlatformMethodReason
Mobile / DesktopAdmin REST API with service role keyCreates pre-confirmed accounts (rider can log in immediately)
Web (Chrome)signUp() via regular Supabase clientBrowsers block service role keys for security

A PostgreSQL trigger (auto_confirm_trigger) auto-confirms all new accounts so riders can log in without email verification.

8. User Roles & Access Control

8.1 Role Detection

After login, the app determines the user's role through a multi-step check in AuthService.getUserRole():

  1. Hardcoded admin check — the root admin email is always recognized as admin
  2. Admins table lookup — queries the admins table by email
  3. Riders table lookup — queries the riders table by email
  4. Fallback — defaults to UserRole.rider

9.8 QR Scanner Verification

File: lib/features/qr_scanner/qr_scanner_screen.dart

Used to verify physical parcel handover by scanning QR codes on shipments.

Scan Flow

  1. Opens device camera using the mobile_scanner package
  2. Displays a targeting overlay (orange-bordered square)
  3. When a QR code is detected, extracts the order ID
  4. Smart parsing: handles both plain text IDs and JSON QR codes ({"order_id": "SDS-123"})
  5. "Ghost-buster": removes invisible/special characters from the scanned text
  6. Updates order status to inTransit and sets verified = true
  7. Shows green success dialog or red error dialog

Manual fallback: "Enter ID Manually" button for cases where QR scanning fails.

A 3-second cooldown prevents duplicate scans.

13. Use Case Scenarios

13.1 Admin Use Cases

UC-1: Admin Logs In

  1. Admin opens the app → sees the login screen
  2. Enters email and password
  3. Supabase Auth validates credentials → JWT token issued
  4. App detects active session → queries admins table → determines role = Admin
  5. Navigates to Admin Dashboard with full navigation

UC-2: Admin Creates an Order

  1. Admin navigates to Orders → taps "New Shipment"
  2. Fills in: sender name/phone, pickup address, receiver name/phone, delivery address, city (dropdown), COD amount, weight
  3. Taps "CREATE"
  4. System generates ID (SDS-{timestamp}), inserts into orders table with status "processing"
  5. Order appears instantly in the list via real-time streaming

UC-3: Admin Assigns Orders to Riders

  1. Admin selects multiple orders via checkboxes → floating batch action bar appears
  2. Auto Assign: System finds all "available" riders, distributes orders via round-robin (even distribution)
  3. Manual Assign: Admin picks a specific rider from a dialog showing name, phone, and status
  4. Order status updates to "assigned", rider_id is set
  5. Assigned rider sees the order in their dashboard immediately (real-time)

UC-4: Admin Registers a New Rider

  1. Admin goes to "Onboard" screen
  2. Fills in login credentials (email, password ≥ 6 chars) and official documents (name, phone, passport, emirates ID, address)
  3. Taps "Register Rider"
  4. System inserts row in riders table → creates Supabase Auth account
  5. Green snackbar: "Rider registered successfully! They can now log in."

UC-5: Admin Monitors Fleet

  1. Admin navigates to "Fleet" screen
  2. Sees all riders with real-time status, contact info, and documents
  3. Can search by name or phone number
  4. Can remove a rider from the system (with confirmation dialog)

UC-6: Admin Verifies Parcel via QR

  1. Admin navigates to "Verify" screen → camera opens
  2. Points camera at parcel QR code
  3. System scans → extracts order ID → updates status to "inTransit" + sets verified = true
  4. Green success dialog appears with order ID
  5. Alternative: taps "Enter ID Manually" if camera scan fails

UC-7: Admin Views Analytics

  1. Admin taps "Generate Report" on the dashboard
  2. Loading indicator while data is fetched
  3. Bottom sheet modal shows: total orders, delivered count, cancelled count
  4. Per-rider performance breakdown (number of deliveries completed by each rider)

13.2 Rider Use Cases

UC-8: Rider Logs In

  1. Rider opens the app → enters email + password (provided by admin at registration)
  2. Supabase Auth validates → app checks riders table → determines role = Rider
  3. Navigates to Rider Dashboard with limited navigation (no Fleet, Onboard, or Settings)

UC-9: Rider Views Their Deliveries

  1. Rider sees their personal dashboard with welcome message using their name
  2. Stats cards show: total deliveries completed, total COD collected (AED)
  3. Active deliveries list shows only orders assigned to them that aren't delivered yet
  4. Each order card shows: order ID, receiver name, city, current status

UC-10: Rider Toggles Duty Status

  1. Rider taps "On Duty" / "Off Duty" toggle button in the header
  2. System updates riders.status to "available" or "unavailable"
  3. Admin sees the change in real-time on the Fleet Management screen
  4. If set to "unavailable", the auto-assignment algorithm skips this rider

UC-11: Rider Verifies Delivery via QR

  1. Rider navigates to the QR scanner screen
  2. Scans parcel QR code → system extracts order ID
  3. Order status updates to "inTransit", verified set to true
  4. Confirms physical handover of the parcel

UC-12: Rider Signs Out

  1. Rider taps the logout icon → confirmation dialog appears
  2. Confirms → Supabase session destroyed → returns to login screen

16. Conclusion

Seven Delivery Service demonstrates a complete, production-ready delivery management system built with Flutter and Supabase. The project showcases:

  • Real-time data streaming — using Supabase Realtime WebSocket subscriptions for instant cross-device updates
  • Role-based access control — two distinct user experiences (admin and rider) from a single codebase
  • Cross-platform deployment — one Dart codebase compiling to Android, iOS, web, and desktop
  • Responsive design — adaptive layouts from mobile (bottom nav) to desktop (side rail with DataTables)
  • QR-based verification — physical parcel handover confirmation using camera scanning
  • Smart assignment algorithms — load-balanced rider distribution for order assignment
  • Material Design 3 — cohesive design system with consistent theming, spacing, and typography
  • Cloud-native architecture — serverless backend with Supabase handling database, auth, and realtime
